# 阶段3报告:Redis 7.2 vs Valkey 9.0 性能基准测试

测试环境:redis:7.2.6、valkey/valkey:9.0.5,本地 Docker(OrbStack),host network 模式,单机 standalone(非集群)。压测工具:`redis-benchmark`/`valkey-benchmark`(与被测引擎版本匹配)。

**测试边界声明**:本地单机 Docker 环境的 CPU/内存由宿主机与压测客户端共享,不代表生产环境独立部署下的绝对性能数值;本阶段的核心目的是获取 **Redis 7.2 与 Valkey 9.0 之间的相对差异**(倍数/百分比),而非追求绝对 QPS 数字的生产可比性。所有测试均在同一台宿主机、同一时间窗口内交替对比测得,以最大程度消除环境噪声对相对差异的影响。

复现方式:`scripts/perf_matrix.sh`(标准吞吐/延迟矩阵,原始输出見 `results/perf/`,该目录已 gitignore,可重新运行脚本生成)。I/O 线程、复制耗时、fork 开销为手动分步验证,命令记录在下文各节。

## 1. 基础吞吐与延迟(不同 value 大小)

固定 `-c 50 -n 100000`,SET+GET 混合:

| value 大小 | 引擎 | 吞吐(rps) | avg延迟(ms) | p50 | p95 | p99 |
|---|---|---|---|---|---|---|
| 128B | Redis 7.2 | 322,580 | 0.093 | 0.095 | 0.151 | 0.175 |
| 128B | Valkey 9.0 | 331,125 | 0.093 | 0.095 | 0.151 | 0.191 |
| 1KB | Redis 7.2 | 316,455 | 0.097 | 0.095 | 0.159 | 0.191 |
| 1KB | Valkey 9.0 | 343,642 | 0.092 | 0.095 | 0.143 | 0.159 |
| 10KB | Redis 7.2 | 241,545 | 0.131 | 0.127 | 0.223 | 0.247 |
| 10KB | Valkey 9.0 | 249,376 | 0.130 | 0.127 | 0.207 | 0.231 |

**结论**:三种 value 大小下 Valkey 9.0 吞吐均**略高于** Redis 7.2(+2.6% ~ +8.6%),延迟分布几乎重合(p50 完全相同,p95/p99 Valkey 略优或持平)。差异幅度不足以称为"显著性能优势",更准确的描述是**两者在标准读写场景下性能基本持平,Valkey 有小幅领先**。

## 2. Pipeline 深度影响

固定 `-c 50 -d 128 -n 200000`:

| pipeline深度 | 引擎 | 吞吐(rps) | p50延迟(ms) |
|---|---|---|---|
| P=1 | Redis 7.2 | 326,797 | 0.087 |
| P=1 | Valkey 9.0 | 351,493 | 0.087 |
| P=16 | Redis 7.2 | 3,030,303 | 0.183 |
| P=16 | Valkey 9.0 | 2,816,901 | 0.223 |
| P=64 | Redis 7.2 | 4,545,454 | 0.575 |
| P=64 | Valkey 9.0 | 4,347,826 | 0.631 |

**结论**:低 pipeline 深度(P=1)时 Valkey 领先约 7.6%;但**随着 pipeline 深度增加,Redis 7.2 反而略微反超**(P=16 领先约7%,P=64领先约4.5%)。差异幅度均在个位数百分比范围内,且这个规模的测试对宿主机瞬时调度噪声敏感(单次运行,未做多轮取平均),**不构成"Valkey pipeline 性能更优"或"更劣"的可靠结论**,只能说明两者在高 pipeline 深度下性能量级相当。

## 3. 全命令套件吞吐(标准 benchmark 默认测试集)

`-c 50 -d 128 -n 100000`,覆盖 PING/SET/GET/INCR/LPUSH/RPUSH/LPOP/RPOP/SADD/HSET/SPOP/ZADD/ZPOPMIN/LRANGE(4档)/MSET/MGET/XADD 等命令:

- 21 项可比命令中,Valkey 9.0 在 **17 项**吞吐持平或领先(多数领先幅度 1%~8%),Redis 7.2 在 **4 项**(LPOP、LRANGE_300、LRANGE_500、LRANGE_600)领先,幅度均在 1%~2% 内。
- Valkey 9.0 的默认测试集比 Redis 7.2 多出 3 项:`MGET (10 keys)`、`FUNCTION LOAD`、`FCALL`(Redis 7.2 的 redis-benchmark 版本默认套件不含这几项),这是压测工具版本差异而非引擎能力差异。
- 最大差距项:`LRANGE_600`(取列表前600个元素)吞吐均较低(Redis 22,026 rps / Valkey 21,267 rps),两者差距在测量噪声范围内(<4%)。

**结论**:全命令套件层面**未发现任何命令存在数量级或两位数百分比的性能差距**,双方在几乎所有标准命令上性能量级一致。

## 4. 高并发连接数(c=200)

`-t set,get -n 200000 -d 128 -c 200`:

| 引擎 | 吞吐(rps) | avg延迟 | p50 | p95 | p99 |
|---|---|---|---|---|---|
| Redis 7.2 | 298,507 | 0.416 | 0.391 | 0.663 | 0.919 |
| Valkey 9.0 | 320,000 | 0.404 | 0.375 | 0.615 | 0.895 |

**结论**:200 并发连接下 Valkey 9.0 吞吐领先约 7.2%,延迟全线（p50/p95/p99）优于 Redis 7.2,是本阶段中 Valkey 领先幅度相对更明显的一项。

## 5. I/O 多线程(io-threads)效果 —— ✅ 确认有效,主要体现在延迟而非吞吐

测试方法:两个独立 Valkey 9.0 实例分别以 `--io-threads 1` 与 `--io-threads 4` 启动,用 `valkey-benchmark --threads 4 -c 500 -d 1024` 施压(多线程压测客户端 + 高并发 + 较大 payload,以确保能触发 I/O 线程激活阈值;实测确认高负载下 `io_threads_active` 从 0 变为 1)。

两轮重复测试结果(SET,取 p50):

| 配置 | 吞吐(rps) | p50延迟(ms) |
|---|---|---|
| io-threads=1(第1轮) | 498,504 | 0.863 |
| io-threads=4(第1轮) | 498,504 | 0.335 |
| io-threads=1(第2轮) | 398,724 | 0.911 |
| io-threads=4(第2轮) | 498,504 | 0.439 |

**结论**:本地单机测试中,吞吐量在两种配置下都被压测客户端/host network 吞吐上限锁死在约 498,504 rps(说明瓶颈不在服务端而在测试环境本身),因此**无法在本地验证"I/O多线程提升吞吐上限"这一官方宣称的场景**(需要真实网卡/多机分离的压测环境,已在计划中标注为本地环境边界之外)。但**两轮重复测试一致显示,开启 io-threads=4 后 p50 延迟稳定降低约 50%~60%**(0.86~0.91ms → 0.34~0.44ms),这是本次验证中观察到的**除高并发场景外最明确的 Valkey 性能优势项**,建议对延迟敏感型客户业务重点验证此项(线上高并发场景通常也是 CPU/网卡资源更充裕的独立物理机部署,吞吐提升可能比本地虚拟化环境测得的更明显)。

## 6. 复制(REPLICAOF)全量同步耗时

测试数据集:约 316,000 个 key,平均 value 512B,`INFO memory` 显示约 244MB 数据量。测量从执行 `REPLICAOF` 到 `master_link_status:up` 的墙钟时间。

| 复制方向 | 耗时 |
|---|---|
| Redis 7.2 → Redis 7.2(基线) | 6.95s |
| Redis 7.2 → Valkey 9.0 | 6.97s |
| Valkey 9.0 → Valkey 9.0 | 7.48s |

**结论**:三种组合耗时几乎一致(差异 <8%,在单次测量噪声范围内),说明全量同步耗时主要由 RDB 生成 + 网络传输 + 加载决定,**引擎差异对全量同步性能没有实质影响**,与阶段1"跨版本复制协议完全兼容"的结论互相印证——不仅协议兼容,性能特征也一致。

## 7. 复制传播延迟(增量写入到副本可见的延迟)

测试方法:在主库连续写入 200 次(每次间隔为下一次写入的等待时间),用 Python 脚本轮询副本直到读到相同值,记录端到端延迟。

| 复制方向 | avg | p50 | p95 | max |
|---|---|---|---|---|
| Redis 7.2 → Redis 7.2(基线) | 0.11ms | 0.11ms | 0.15ms | 1.25ms |
| Redis 7.2 → Valkey 9.0 | 0.13ms | 0.11ms | 0.22ms | 1.46ms |

**结论**:两者 p50 完全一致,p95/max 差异在亚毫秒级(本地 loopback 网络噪声范围内)。**增量复制传播延迟无实质差异**,不会给现有基于复制延迟做读写分离/一致性判断的业务逻辑带来行为变化。

## 8. Fork / BGSAVE 开销(同等数据集,~316K key / ~244MB)

多次 `BGSAVE` 测量 `INFO stats` 中的 `latest_fork_usec`:

| 引擎 | 测量1 | 测量2 | 测量3 |
|---|---|---|---|
| Redis 7.2 | 3,570μs | 1,677μs | 1,517μs |
| Valkey 9.0 | 1,311μs(首次)/ 979μs | 1,065μs | 989μs |

首次 BGSAVE 总耗时(含日志阶段完成时间轮询):Redis 7.2 约 0.87s,Valkey 9.0 约 0.62s。

**结论**:在约 244MB 数据集规模下,Valkey 9.0 的 fork 耗时**稳定低于** Redis 7.2 约 30%~55%(排除 Redis 首次测量的异常值后,稳态对比约 1.3~1.7ms vs 1.0ms 左右),BGSAVE 总耗时也快约 29%。这与官方宣称的 fork COW 优化方向一致。**但本地测试数据集规模(244MB)远小于生产环境常见的数GB~数十GB实例**,fork 耗时通常随数据集大小(准确说是页表项数量)近似线性增长,244MB 规模下的绝对差异(微秒级)在生产可感知的影响有限;真正需要关注的是**大数据集(如10GB+)下 fork 耗时的相对优势是否被放大**,这部分留给阶段4稳定性测试用更大数据集专项验证。

## 阶段3结论汇总

| 维度 | 结论 | 幅度 |
|---|---|---|
| 基础 SET/GET 吞吐延迟 | Valkey 略优 | +2.6%~+8.6% 吞吐,延迟基本持平 |
| Pipeline 深度影响 | 双方互有胜负,均在噪声范围 | ±4%~8%,无一致趋势 |
| 全命令套件 | 双方持平,无量级差距 | 17/21 项 Valkey 微弱领先,幅度均 <8% |
| 高并发连接(c=200) | Valkey 领先,吞吐延迟双优 | +7.2% 吞吐,延迟全线更优 |
| I/O 多线程(io-threads) | **确认有效,主要降延迟** | p50 延迟降低约 50%~60%(吞吐受限于本地测试环境未验证到) |
| 复制全量同步耗时 | 无实质差异 | <8%,噪声范围 |
| 复制增量传播延迟 | 无实质差异 | p50 完全一致 |
| Fork/BGSAVE 开销(244MB数据集) | Valkey 明显更优 | fork 耗时低 30%~55%,BGSAVE 总耗时快约 29% |

**总体结论**:在本地单机标准读写场景下,**Valkey 9.0 相较 Redis 7.2 没有数量级或颠覆性的性能优势**,大多数命令/场景下双方性能量级相当(差异在个位数百分比,不足以成为迁移的独立驱动力)。但有两个方向的优势具备一定确定性、值得作为迁移的加分项而非唯一理由:(1)**I/O 多线程对延迟的改善**,对延迟敏感业务有实际意义;(2)**fork/BGSAVE 开销更低**,对大数据集实例、频繁 BGSAVE(备份策略密集)或对 fork 期间延迟毛刺敏感的场景有直接收益,阶段4将用更大数据集验证该优势是否随规模扩大。**性能不应作为"必须升级"的核心论据,但也未发现任何性能倒退风险**——这与阶段1"兼容性无损"的结论共同支持"迁移是安全的,收益主要来自模块生态和运维改进,性能是锦上添花"这一定位。
