# 阶段4报告:稳定性与资源画像

测试环境:redis:7.2.6、valkey/valkey:9.0.5,本地 Docker(OrbStack),host network 模式。本阶段覆盖三个子专项:(1) fork/BGSAVE 开销随数据集规模的扩展性;(2) 内存碎片率与主动碎片整理效果;(3) 故障注入(kill 主节点 failover、网络分区/脑裂防护)。

**测试边界声明**:内存 soak test 部分因交互式验证周期限制,采用**压缩加速方法**(持续高强度写入/删除/过期负载在 30 分钟内注入,而非真实 24-48 小时挂钟时间的自然业务负载),用于在短时间内触发内存分配器的可观测状态变化,而非模拟真实生产环境下碎片率随时间自然增长的时间尺度。如实记录该方法论边界,避免读者误认为是 24-48 小时真实观察结果。

复现方式:`scripts/fork_scaling_test.sh`、`scripts/soak_test.sh`、`scripts/failover_test.sh`、`scripts/fault_inject.sh`、`scripts/cluster.sh` / `scripts/cluster_join.sh`。

## 1. Fork / BGSAVE 开销随数据集规模扩展 —— ⚠️ Valkey 优势随规模增大而收窄

在同一对 standalone 实例(容器 `ve-stab-redis`/`ve-stab-valkey`)上,通过增量写入将数据集逐步做大,每个规模节点触发 3 次 `BGSAVE`,记录 `INFO stats` 中的 `latest_fork_usec`:

| 数据集规模(实际 used_memory) | key 数量 | Redis 7.2 fork_usec(3次) | Redis 均值 | Valkey 9.0 fork_usec(3次) | Valkey 均值 | Valkey 领先幅度 |
|---|---|---|---|---|---|---|
| ~165MB | 242,689 / 242,094 | 1540 / 832 / 797 | 1056μs | 712 / 715 / 728 | 718μs | **32.0%** |
| ~1GB(960MB/931MB) | 1,405,572 / 1,405,722 | 3902 / 3902 / 3787 | 3864μs | 3656 / 3002 / 2825 | 3161μs | **18.2%** |
| ~1.7GB(1.65GB/1.68GB) | 2,413,447 / 2,412,815 | 6983 / 6983 / 5548 | 6505μs | 5982 / 5982 / 5197 | 5720μs | **12.1%** |

**关键发现**:阶段3(244MB 规模)测得 Valkey fork 耗时低 30%~55%,本阶段用更大数据集复测后发现**这一优势幅度随数据集增大而系统性收窄**——165MB 时约 32%,1GB 时降至约 18%,1.7GB 时进一步降至约 12%。两个引擎的 fork_usec 绝对值都随数据集大小近似线性增长(符合 fork 系统调用复制页表项的开销模型),但 Redis 的增长斜率略陡于 Valkey,这是两者差距收窄而非扩大的原因——**不能简单外推阶段3"30%~55%更快"的结论到生产环境常见的数GB~数十GB实例规模**;基于目前观测到的收窄趋势外推,在生产典型的10GB+实例上,fork 耗时优势可能进一步收窄至个位数百分比甚至趋于持平。该趋势具有参考价值,但受限于本地环境未能测试更大规模(受限于压测工具灌入速度与验证周期,未测试10GB+梯度),建议不作为决策的核心依据,仅作为"fork优化存在但幅度会随规模增大而减弱"的方向性提示。

## 2. 内存碎片率:大 value 分配/删除模式 —— ✅ 碎片产生与整理效果一致

**方法**:标准的碎片诱导模式——先用 `redis-benchmark -t set -d 4096` 灌入 50 万个 4KB value(约 500,000 keys),再用 `SCAN`+随机 70% 概率 `DEL` 制造大量分配空洞,观测 `mem_fragmentation_ratio` 变化,随后开启 `CONFIG SET activedefrag yes` 观察 30 秒内的整理效果。

| 阶段 | Redis 7.2 | Valkey 9.0 |
|---|---|---|
| 灌入后(删除前) | frag=1.01 | frag=1.01 |
| 删除 ~70% key 后 | used_memory=498MB, rss=1662MB, **frag=3.34** | used_memory=496MB, rss=1656MB, **frag=3.34** |
| 开启 activedefrag 30s 后 | rss=565MB, **frag=1.13** | rss=554MB, **frag=1.12** |

**结论**:两个引擎的内存分配器均为 `jemalloc-5.3.0`(版本一致),碎片产生模式(大量删除后碎片率从 1.01 飙升到 3.34)与主动碎片整理的收敛速度(30秒内降回约 1.12~1.13)**几乎完全一致**,未发现 Valkey 在内存分配/整理层面存在行为差异或回归风险。`activedefrag` 默认关闭(与 Redis 一致),配置项语义无变化。

**补充:持续同尺寸覆写负载下的碎片趋势(压缩加速 soak test,30分钟,15秒采样)**——用持续的"变长value写入(64B/8KB/64KB混合)+随机删除+短TTL被动过期"混合负载模拟长期运行场景,结果详见 `results/stability/soak-{redis,valkey}.csv`。此负载模式下两引擎的 `mem_fragmentation_ratio` 全程稳定在 1.01,未观测到碎片率随时间增长的趋势——这与上面"大量单向删除"测试形成对照,说明**碎片增长主要由"分配后大批量释放且不再复用相近尺寸"的模式触发,而非任意写删混合负载都会导致碎片累积**,两引擎在这一行为特征上表现一致,均受益于 jemalloc 的尺寸分级(size class)复用机制。

## 3. 故障注入:kill 主节点 failover 耗时与数据一致性 —— ✅ 表现一致,均在预期范围内

**方法**:分别搭建 6 节点集群(3主3从,`cluster-node-timeout 5000`,默认配置),对同一 master 写入基线 key 后 `docker kill -SIGKILL` 掉该 master 容器,轮询其副本的 `ROLE` 直至变为 `master`,记录墙钟耗时;并验证 kill 前写入的 key 在新 master 上是否可读(数据一致性)。每个引擎重复 3 次(依次 kill 集群中的每个 master)。

| 引擎 | 试验1 | 试验2 | 试验3 | 均值 |
|---|---|---|---|---|
| Redis 7.2 | 8.480s | 7.673s | 8.471s | **8.208s** |
| Valkey 9.0 | 7.276s | 7.745s | 7.525s | **7.515s** |

- 3 次试验中,两个引擎均**未出现数据丢失**(kill 前写入的 key 在新 master 上均可正确读到)。
- failover 完成后 `cluster_state` 均恢复为 `ok`,集群拓扑正确剔除故障节点、新 master 正确接管原 slot 范围。
- Valkey 均值耗时略低于 Redis(约低 8%),但两者耗时主要由 `cluster-node-timeout`(默认5000ms)+ 故障检测投票延迟决定,是集群协议参数而非引擎实现差异主导的开销,**8%的差异在此机制的正常抖动范围内,不构成显著性能结论**。云平台若需要更快的 failover 响应,应重点调优 `cluster-node-timeout` 等超时参数,这对两个引擎同样适用。

## 4. 网络分区/脑裂防护行为 —— ✅ 行为一致,无脑裂风险

**方法**:用 `docker kill -SIGSTOP`(而非 SIGKILL)模拟主节点假死/网络分区(进程存活但完全无响应,不同于进程终止),在 6 节点集群(3主3从)上对某个 master 执行:
1. 写入基线 key
2. SIGSTOP 该 master 容器
3. 轮询其副本,确认在 `cluster-node-timeout` 后被其他节点判定 `FAIL` 并完成 failover(副本 `ROLE` 变为 master)
4. `SIGCONT` 恢复原 master 进程
5. 检查原 master 恢复后的自我认知(是否会继续认为自己是 master 从而造成脑裂)、是否接受直接写入、集群整体状态是否收敛回 `cluster_state:ok`

| 检查项 | Redis 7.2 | Valkey 9.0 |
|---|---|---|
| 副本在原 master 假死后被提升 | ✅ 是(约7-15次200ms轮询内) | ✅ 是(约16次300ms轮询内) |
| 原 master 恢复后自我角色 | **自动降级为 slave** | **自动降级为 slave** |
| 原 master 恢复后能否接受直接写 | ❌ 拒绝,返回 `MOVED <slot> <新master地址>` | ❌ 拒绝,返回 `MOVED <slot> <新master地址>` |
| kill 前写入的基线 key 恢复后是否可读(经新 master) | ✅ 值正确(`value-before-partition`) | ✅ 值正确(`value-before-partition`) |
| 集群整体状态恢复 | `cluster_state:ok` | `cluster_state:ok` |

**结论**:两个引擎在"网络分区导致原 master 与集群失联并被替换,分区恢复后原 master 重新加入"这一经典脑裂风险场景下,表现**完全一致**——都依赖 Redis Cluster 协议本身的 epoch/configEpoch 机制,让重新加入的旧 master 识别到自己的 epoch 落后于新 master,从而**自动降级为副本而非产生双写**。这是 Redis Cluster 协议层面的保证(而非某个引擎的独有实现),Valkey 9.0 完整保留了这一行为,**未发现任何弱化脑裂防护的回归风险**。

需要特别说明的边界:本测试用的是**单个 master 的短暂假死**(SIGSTOP 几秒到十几秒),不是真正的多机网络分区(如两侧网络完全隔离且双方都保有一部分客户端连接的"双活脑裂"场景)。真正的多机网络分区测试(如用 `tc netem`/`pumba` 制造双向丢包)受限于本地单机 Docker host network 模式无法模拟真实网络分区拓扑(所有容器共享同一网络栈,无法对特定容器对做单向断网),**留作已知的本地环境测试边界**,不影响本节已验证结论(集群协议层脑裂防护机制两引擎一致)的有效性。

## 阶段4结论汇总

| 维度 | 结论 | 风险/说明 |
|---|---|---|
| Fork/BGSAVE 开销(小数据集) | Valkey 明显更优(约30-55%) | 阶段3结论,适用于 <300MB 级别小实例 |
| Fork/BGSAVE 开销(规模扩展性) | **优势随规模增大而收窄**(32%→18%→12%,165MB→1GB→1.7GB) | 生产大实例(10GB+)优势可能进一步收窄,不宜直接外推阶段3结论 |
| 内存碎片产生模式 | 两引擎完全一致(jemalloc 5.3.0 相同) | 无风险,无需针对碎片行为做迁移适配 |
| 主动碎片整理(activedefrag)效果 | 两引擎收敛速度和幅度一致 | 无风险,配置项语义不变 |
| 长期同尺寸覆写负载碎片趋势 | 两引擎均保持稳定,无碎片累积 | 无风险(压缩加速测试,非24-48h真实挂钟观察) |
| Kill 主节点 failover 耗时 | 两引擎耗时量级一致(Valkey 均值低约8%,在协议超时参数抖动范围内) | 无风险,均无数据丢失 |
| 网络分区/脑裂防护 | 两引擎行为完全一致,均无脑裂风险 | 无风险,协议层保证,非引擎相关 |

**总体结论**:稳定性维度**未发现任何 Valkey 相较 Redis 7.2 的回归风险**——内存分配/碎片整理行为一致、故障探测与 failover 时间量级一致、脑裂防护机制一致(源于共享的 Redis Cluster 协议基础)。唯一需要修正认知的是 **fork/BGSAVE 性能优势不是一个固定百分比,而是随数据集规模增大而收窄的曲线**,云平台如果计划以此作为迁移收益点对外宣传,应基于目标客户的典型实例规模使用对应规模区间的实测数据,而非笼统引用阶段3的小数据集结果。故障恢复与脑裂防护两项直接关系到"能否安全迁移"的核心问题,**结论是肯定的**:Valkey 9.0 在这些高风险场景下的行为与 Redis 7.2 完全等价。
