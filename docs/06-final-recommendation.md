# 阶段6:汇总与决策建议 —— Redis 7.2 → Valkey 9.x 升级可行性最终结论

**范围声明**:本报告仅评估技术可行性,不涉及 License 维度的评估(按项目启动时的约定排除)。以下结论均基于本项目 1-5 阶段的实测数据与可复现脚本(见 `docs/01`~`docs/05` 及 `results/`、`scripts/`),引用第三方数据处均已明确标注来源。

## 一、核心结论:能否 100% 支持现有用户无损升级?

**不能给出无条件的"是"。结论是:对绝大多数用户画像可以给出高置信度的"是",但存在一项在大规模集群场景下被实测确认的严重缺陷(阶段5),使得"100%无损"这一表述在当前 Valkey 9.0.5 版本下不成立,必须作为前置风险披露,而非可以忽略的边缘情况。**

具体展开为三类用户画像的分别结论(见第三节)。这与项目最初调研阶段"重点关注模块生态缺口"的预期不同——**实测中最大的风险点不是模块能力(该项已有清晰的用户画像划分方案),而是大规模集群批量故障场景下的稳定性回归**,这是调研阶段未能预见、只能通过实测发现的问题,也印证了本项目"以实测为主"的方法论选择是必要且正确的。

## 二、九个验证维度结论总览

| # | 维度 | 结论 | 风险等级 | 证据来源 |
|---|---|---|---|---|

| 3 | 集群滚动升级路径 | 逐分片加副本→failover→摘旧节点,完整验证通过 | 无风险 | 阶段1 §3 |
| 4 | 行为差异(AUTH顺序等) | 1项确认差异(NOAUTH行为),影响面有限且可排查 | 低风险 | 阶段1 §4 |

## 三、按用户画像分类的升级建议

### 画像A:标准用户(无 Redis Stack 模块依赖,标准数据结构/命令为主)—— ✅ 可以升级,但需接受第10项风险披露

- 数据、复制、集群滚动升级路径、客户端库、绝大多数运维接口均已验证无损兼容。
- **前置条件(见第五节)**:云平台必须先完成阶段5发现的崩溃问题的官方确认与修复验证,或至少制定针对该场景的缓解预案(如限制单次故障域范围、加强多可用区隔离降低批量关联故障概率、上线前用目标集群规模做二次验证),才能对这批用户做出"无损"承诺。
- 在崩溃问题解决前,建议优先向**集群规模较小(如 <20 分片)或部署了充分故障域隔离(多可用区、机架反亲和)、批量关联性故障概率低**的用户开放升级,规模化推广应等待官方修复确认。

### 画像B:使用 RedisJSON / RedisBloom 的用户 —— ✅ 可以升级,能力对等

- ValkeyJSON 与 RedisJSON 数据类型(`ReJSON-RL`)、RDB 兼容性、核心命令行为均对等,valkey-bloom 基本命令验证通过。
- 同样需要遵循画像A的前置条件。

### 画像C:使用 RediSearch(尤其纯文本/TAG/数值检索,不涉及向量)或 RedisTimeSeries 的用户 —— ⚠️ 需业务侧改造,暂不建议直接升级

- valkey-search 当前版本(通过 `valkey-bundle:9.0` 镜像实测)**强制要求 schema 中包含向量字段才能创建索引**,无法承接纯文本全文检索、TAG过滤、数值范围查询等不涉及向量的场景——这是能力缺失而非性能落后,比调研阶段预期的"向量检索性能落后27%"更严重。
- RedisTimeSeries 无官方对应模块,确认无替代方案。
- 建议:这批用户在官方推出对等能力前,继续保留在 Redis 侧,或评估业务侧改造为自建时序/检索方案的可行性与成本。

### 画像D:依赖未认证连接报错类型做探测逻辑,或直接位置解析 CLUSTER SHARDS 等数组型运维接口的用户 —— ⚠️ 需要代码/工具排查,非阻塞

- 排查成本低(见阶段1 §4、阶段2 §2/§6 的具体排查清单),完成排查确认无影响后即可归入画像A。

## 四、推荐迁移路径(基于阶段1验证)

1. **单机/主从架构**:使用 REPLICAOF 路径——Valkey 9.0 挂载为运行中 Redis 7.2 主库的副本,全量同步完成、`master_link_status:up` 后,业务侧短暂静默写入(建议数秒),执行 `REPLICAOF NO ONE` 完成 promote,恢复写入。全程监控复制 offset 差值确保追平。
2. **集群架构**:使用"逐分片滚动升级"路径——对每个分片,先给 Redis 主节点挂载一个 Valkey 副本(利用集群总线互通性,`CLUSTER MEET` 可直接跨引擎加入),验证数据一致后对该 Valkey 副本执行 `CLUSTER FAILOVER`(slot 分配不变),原 Redis 节点自动降级为副本,再用 `--cluster del-node` 摘除。建议单分片操作之间保留观察间隔,确认集群健康后再处理下一分片。
3. **回滚预案**:两条路径在 promote/failover 之前都保留原 Redis 节点存活且数据可用,若中途发现问题可直接停止升级流程、不摘除 Redis 节点即可保持原状;一旦摘除 Redis 节点(集群路径的最后一步)或执行 `REPLICAOF NO ONE` 完成读写切换后,由于 RDB/AOF 格式不兼容 Redis 7.4+ 工具链,**无法再回退使用更新版本的 Redis 生态工具**,只能视为"已完成迁移,后续只能在 Valkey 生态内前进或依赖 7.2 版本工具回退"——这一点必须在迁移前对用户/团队明确说明,是本次评估开始就已明确的既定风险,不因本次实测结果改变。
4. **灰度策略建议**:结合第三节的画像分类,先在画像A中风险最低的子集(小规模集群、非模块依赖用户)灰度,同时跟踪官方对阶段5崩溃问题的响应,再逐步扩大灰度范围。

## 五、上线前必须完成的前置事项(基于阶段5发现)

1. 向 Valkey 官方仓库提交阶段5发现的崩溃复现报告(断言 `cluster_legacy.c:3842 'link != sender->link' is not true`,触发条件为集群中约30%比例的master节点在短时间窗口内同时失效),已保存完整堆栈与节点日志(`results/large-cluster/`)。
2. 跟踪官方修复进度,在候选修复版本发布后,使用本项目已验证的 `scripts/cluster.sh`/批量kill方法论重新测试,确认问题解决。
3. 在完全确认修复前,任何面向大规模集群客户的"无损升级"对外承诺都应附带该已知风险的说明,并优先安排故障域隔离良好、批量关联性故障概率较低的客户群体。
4. 补充验证崩溃场景下是否存在真实业务数据丢失(本次测试为空数据集的纯拓扑验证,建议补测真实数据量下的一致性)。
5. **不要假设"修复了阶段5发现的具体崩溃点,千节点规模的批量故障场景就是安全的"**。详见 `docs/07-large-scale-theoretical-analysis.md` 的理论分析:`cluster_legacy.c` 中集群总线连接状态与消息处理的一致性问题历史上已反复出现(至少3个独立实例,含阶段5发现),且 Valkey 官方自己在2000节点规模做批量失效测试时也发现了此前未知的新bug(活锁类,#2181)。若未来计划以千节点级单集群承载生产流量,上线前应针对批量关联性故障场景专门做规模对等或同量级的实测验证,而非仅凭个别bug修复即认为已覆盖风险。

## 六、本次评估的方法论边界(供报告读者判断结论适用范围)

- 全部测试基于单机 Docker(OrbStack)环境,不代表生产环境独立部署的绝对性能数值,但相对差异(Redis vs Valkey 的比较)具有参考价值。
- 300节点及以上规模的批量故障对比测试因本地 Docker daemon 资源耗尽崩溃而未能完成,该规模下的结论基于100节点数据外推,详见阶段5边界声明。1000+节点规模已改为理论分析(`docs/07-large-scale-theoretical-analysis.md`),基于官方1B RPS基准数据、gossip协议复杂度分析与GitHub历史issue交叉推演,非本项目直接实测。
- 内存 soak test 采用30分钟压缩加速方法,非真实24-48小时观察。
- 网络分区测试使用 SIGSTOP 模拟单节点假死,非真实多机网络隔离(本地单机 host network 模式无法模拟真实网络分区拓扑)。
- fork/BGSAVE 性能优势的规模外推样本上限约1.7GB,未覆盖生产常见的数GB~数十GB实例规模。

## 七、写在最后

本项目最初的调研假设是:Valkey 9.x 相较 Redis 7.2 的主要风险点集中在模块生态(RediSearch/RedisTimeSeries 能力缺口)和大规模集群性能验证的可行性边界。五个阶段的实测总体上验证了这一假设在**兼容性、性能、常规稳定性**维度是准确的——这些维度均未发现值得阻塞升级决策的问题。

但阶段5的发现说明:**"文档调研 + 小规模验证"不足以支撑"100%无损"这一强承诺**,大规模集群下的批量关联性故障是一类只有通过实测才能捕捉到的风险类别,且该发现具备复现性、确定性、非环境噪声等一系列可以支撑其"这是真实缺陷而非测试假象"的证据特征。这也是本项目坚持"以实测为主、文档为辅"这一方法论的核心价值所在。

**最终建议**:批准 Valkey 9.x 作为 Redis 7.2 的下一代托管引擎选型方向,技术路径(数据兼容、迁移路径、客户端兼容、性能)已充分验证可行;但在正式面向存量用户开放规模化升级前,**必须先解决或规避阶段5发现的大规模集群批量故障崩溃问题**,这是当前唯一阻断"无条件100%无损承诺"的技术因素。
