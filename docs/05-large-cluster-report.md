# 阶段5报告:大规模集群拓扑验证

测试环境:redis:7.2.6、valkey/valkey:9.0.5,本地 Docker(OrbStack),host network 模式,单机多容器模拟集群节点(容器名 `ve-lc-<engine><规模>-<四位序号>`,数据目录 `.data/`,均不入库)。

**测试边界声明(重要,先于结论说明)**:

1. 本阶段最初计划验证 300 节点规模。在实际执行中,同时运行 redis300 + valkey300 共 600 个 host-network 容器时,OrbStack 内部的 Docker daemon/VM 在批量重启容器操作下发生**崩溃**(`docker info` 报告 "Cannot connect to the Docker daemon",需要 `orb start` 显式重启虚拟机才能恢复)。这证实了计划文档中预先声明的"本地单机资源上限"边界是真实存在的,而非过度保守的预估。因此,**本阶段的批量故障恢复(batch-kill)对比实验最终在 100 节点规模完成**,300 节点规模仅完成了拓扑创建与 gossip 收敛验证(见下文第1节),未能完成 300 节点规模的 batch-kill 对比。这是本地环境的资源边界,不代表 Valkey/Redis 在真实分布式部署下的规模上限——真实生产环境的 300+ 节点集群跑在独立物理机/虚拟机上,不存在"600个容器抢占同一台笔记本内核资源"这种人为瓶颈。
2. 100 节点规模下发现的 Valkey 节点崩溃问题(见第3节)是**本阶段最重要的发现**,其严重性使得没有必要冒着再次冲击本地环境稳定性的风险去追求 300 节点规模的达成率——一个在 100 节点规模下就能稳定复现的崩溃缺陷,其结论有效性不依赖于更大规模的重复验证。

复现方式:`scripts/cluster.sh create/join`、`scripts/failover_test.sh`,以及本节手工记录的 `CLUSTER MEET`/批量 `docker kill` 操作(命令见下文各节)。

## 1. Gossip 协议收敛(100节点集群,新节点加入)

**方法**:向已运行的 100 节点集群(50主50从,`cluster-node-timeout 5000`)执行 `CLUSTER MEET` 加入一个全新的第 101 个独立节点,轮询新节点自身的 `cluster_known_nodes`,记录其从 1(仅自己)增长到 101(得知全部节点)所需的墙钟时间。

| 引擎 | 收敛耗时(1→101个已知节点) |
|---|---|
| Redis 7.2 | 545ms(11次轮询,每次间隔50ms) |
| Valkey 9.0 | 未完整测得(见下方说明) |

**说明**:Valkey 侧的等效测试因第3节所述的节点崩溃问题在测试窗口内反复触发(集群处于故障恢复/配置不一致状态,不是执行 gossip 收敛测试的干净基线),未能取得可信的独立测量值。这是**该测试本身的执行顺序问题**(应先做纯拓扑测试再做故障注入,或用完全独立的集群做两类测试),不代表 Valkey gossip 收敛能力有缺陷。此前(见阶段5中间记录,300节点规模)曾观测到两引擎在 300 节点规模下 gossip 收敛均可在2秒内完成,量级上无明显差异。**结论**:gossip 收敛机制在两引擎间的可用测量数据点上没有发现显著差异,该项建议在独立、无并发故障注入的环境下补测 Valkey 侧数据以完善对比,但不影响本阶段最主要的发现(第3节)。

## 2. 批量故障恢复:Redis 100节点集群(30% master同时kill) —— ✅ 自动恢复,无崩溃

**方法**:100节点集群(50主50从),同时 `docker kill -SIGKILL` 15个master(占master总数30%,复现真实场景中"一个可用区/机架整体下线"级别的关联性故障),轮询存活节点的 `cluster_state`,并用 `--cluster check` 确认槽位覆盖的真实性(而非仅凭 `cluster_state:ok` 判断,因为 gossip 收敛与槽位覆盖收敛可能存在时间差)。

- kill 时刻 → `cluster_state:ok`:**30秒**(9次轮询,每次间隔2秒)
- `--cluster check`:`[OK] All 16384 slots covered.`,无孤立槽位、无节点配置分歧
- **全部15个被kill的master均由其副本自动完成 failover,无一卡死**——这与本阶段中间过程中在 300 节点规模观测到的现象(13/30个副本因 `cluster-replica-validity-factor` 保护机制卡在自动failover未完成、需要人工 `CLUSTER FAILOVER FORCE` 干预)形成对照:**该 validity-factor 卡死现象在100节点规模下未复现**,提示这是一个与"故障检测/投票过程在大规模拓扑下完成所需时间"相关的规模敏感问题,而非固定阈值配置错误——在小规模集群下,故障检测本身足够快,能在 `cluster-replica-validity-factor`(默认10)×`cluster-node-timeout`(默认5000ms)=50秒的有效性窗口内完成,但在 300 节点规模下,同等的检测/投票延迟被拉长,导致部分副本的失联时间在能够被判定+提升之前就已超过该窗口。
- **无数据一致性问题**(本轮测试为纯拓扑/协议验证,未加载业务数据,一致性验证已在阶段4的6节点集群测试中单独覆盖并确认无数据丢失)

## 3. 批量故障恢复:Valkey 100节点集群(30% master同时kill) —— 🔴 严重发现:批量故障触发级联节点崩溃

**方法**:与第2节完全相同的操作——100节点集群(50主50从),同时 kill 15个master(30%)。

**观测到的现象**:

- kill 后约1-8分钟内,**85个存活节点中有30个(19个master + 11个replica)先后崩溃退出**(容器 exit code 133 = SIGABRT,另有1例 exit code 139 = SIGSEGV),而非保持存活参与故障恢复。
- 全部30次崩溃的日志均包含**完全相同的断言失败**:
  ```
  === ASSERTION FAILED ===
  ==> cluster_legacy.c:3842 'link != sender->link' is not true
  ```
  崩溃发生在集群消息处理路径(`clusterProcessPacket` → `clusterReadHandler`),即节点在处理来自其他节点的 gossip/集群总线消息时触发。
- 尝试 `docker start` 重启全部30个崩溃节点后,其中3个节点(2个master + 1个replica)在重启后**再次于几分钟内触发同一断言崩溃**(观测到 `ve-lc-valkey100-0090` 重启后于10分钟内二次崩溃,日志中断言位置完全相同),形成**崩溃循环(crash loop)**,证实这不是一次性偶发事件,而是可复现的确定性缺陷(在集群处于该故障后的特定状态下,只要节点存活并继续处理集群消息就会再次触发)。
- 最终集群状态:`cluster_state:fail`,`redis-cli/valkey-cli --cluster check` 报告 `[ERR] Nodes don't agree about configuration!` 与 `[ERR] Not all 16384 slots are covered by nodes.`——**这是一个真实的、未自愈的槽位不可用状态**,而非临时的 gossip 收敛延迟。

**与 Redis 侧对比**:Redis 7.2.6 在完全相同的操作(kill 15/50 masters)下,**零崩溃**,30秒内自动恢复全部槽位覆盖(见第2节)。

**严重性评估**:

- 已通过 GitHub 搜索确认,这一具体断言(`cluster_legacy.c:3842 'link != sender->link'`)**未见于 Valkey 官方已知 issue 列表**(搜索到的是其他不同位置/条件的 cluster_legacy.c 断言,如 configEpoch 校验、gossip 消息乱序等相关但不同的问题),初步判断为一个尚未被广泛报告的缺陷,而非已知且已有修复计划的问题。
- 崩溃波及**master 节点**(19个),这意味着**该缺陷不仅影响可用性,还直接关系到数据完整性**——一个持有实际业务数据分片的 master 在批量故障恢复过程中崩溃退出,如果崩溃发生在 RDB 落盘之前或与副本同步不完整的窗口期,存在数据丢失风险(本轮测试未加载业务数据,该风险点为逻辑推断,未直接实测验证,建议作为后续必须补充验证的项)。
- 触发条件(15个master同时失效,占比30%)对应真实生产场景中**可用区级别故障、机架整体断电、批量宿主机维护窗口误操作**等并非罕见的关联性故障模式,不是极端边缘情况。
- **这是本项目迄今为止发现的唯一一项能够直接推翻"Valkey 9.0 可无损兼容替代 Redis 7.2"结论的技术证据**——此前阶段1-4的所有测试均未发现回归风险,本项发现足以让"能否100%支持现有用户升级"这一核心问题的答案从"是"变为"有条件的是,前提是这一崩溃问题被修复或规避"。

**建议的后续行动**(需在阶段6最终建议中体现):
1. 向 Valkey 官方仓库(https://github.com/valkey-io/valkey/issues)提交该崩溃的详细复现步骤与完整 crash report(已保存崩溃节点的完整日志,含堆栈与 `INFO`/`CONFIG` 快照),确认是否为已知问题、是否已在更新版本修复。
2. 在正式上线前,**必须在更高 Valkey 版本(如未来的9.0.x补丁版本或9.1.x)下复测本项**,确认该问题是否已被修复;若未修复,**不建议在大规模集群(尤其是 replica 数量较多、批量故障概率较高的部署)场景下升级到 Valkey 9.0.5**,至少应等待官方修复。
3. 补充验证崩溃发生时是否存在实际数据丢失(需要加载真实业务数据后重跑本实验,验证重启恢复后的数据完整性,而非仅验证拓扑层面的槽位覆盖)。

## 阶段5结论汇总

| 维度 | 结论 | 风险/说明 |
|---|---|---|
| Gossip收敛(100节点新节点加入) | Redis测得545ms;Valkey因崩溃问题未测得干净数据 | 需要补测,不影响主要结论 |
| 批量故障恢复(30% master同时失效,100节点) | Redis:30秒自动恢复,零崩溃;Valkey:**30/85节点崩溃,集群故障未自愈** | 🔴 **严重回归风险**,详见第3节 |
| 300节点规模测试 | 因本地Docker daemon资源耗尽崩溃,未完整完成 | 本地环境边界,非引擎能力问题;但已被第3节发现的严重性取代其测试优先级 |
| Redis侧 `cluster-replica-validity-factor` 卡死现象(300节点中间观测) | 100节点规模下未复现,提示为规模敏感的故障检测时序问题而非固定配置缺陷 | 建议生产环境按目标集群规模适当调优 `cluster-node-timeout` 等参数,该建议对两引擎同样适用 |

**总体结论**:阶段5是本次评估中**唯一发现严重、可复现回归风险的阶段**。与阶段1-4"未发现显著回归"的基调不同,100节点规模下 30% master 批量同时失效场景在 Valkey 9.0.5 上触发了确定性的、可复现的集群消息处理断言崩溃(`cluster_legacy.c:3842`),导致高比例节点(35%)崩溃退出且集群未能自愈恢复槽位覆盖——这与 Redis 7.2.6 在完全相同条件下的零崩溃、30秒自动恢复形成鲜明对比。**该发现直接影响阶段6"能否100%支持现有用户升级"的最终结论**,建议在最终建议中明确标注:大规模集群(尤其是历史上经历过或可能经历批量关联性故障的部署)在未确认此问题已修复前,**不建议采用 Valkey 9.0.5**,或至少需要将此风险与缓解计划(向官方报告、等待补丁、上线前在目标版本重新验证)作为升级决策的前置条件。
